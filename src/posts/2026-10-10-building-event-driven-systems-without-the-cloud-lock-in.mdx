I've been working with AWS infrastructure for quite some time, especially with DynamoDB, EventBridge, and Lambda to build event-driven systems.

I've always liked how practical this approach is. You can connect services through events, keep components decoupled, and go from an idea to something scalable with very little infrastructure to manage.

For event-driven workloads, Lambda fits particularly well into this model. You write a small handler, connect it to an event source, and let AWS take care of running and scaling it.

That simplicity is one of the things I like most about the AWS ecosystem.

But as I started using this model more, some of the trade-offs became harder to ignore.

Even a relatively small application can generate a surprising amount of event traffic. With usage-based services, cost tends to follow the number of events and the number of steps they pass through rather than the size of the application itself.

A single change might flow through DynamoDB Streams, EventBridge, and one or more Lambda functions. Each individual service can be inexpensive, but as event volume and fan-out grow, so does the number of operations involved.

There is also the bigger issue of vendor lock-in. The more of these services you combine, the more the architecture itself becomes tied to AWS.

And Lambda, while a great fit for event processing, starts to feel different when you use it for workloads that are naturally long-running services.

APIs are a good example.

## Where Lambda Starts to Feel Less Simple for APIs

Lambda works really well for APIs, especially when the workload is small, stateless, and bursty.

But as the API grows, some of that simplicity starts to disappear.

Cold starts may require Provisioned Concurrency or SnapStart. More advanced HTTP needs often bring API Gateway into the architecture. Relational databases can require RDS Proxy to reduce connection pressure. WebSockets, long-running requests, or steady workloads may push you toward other AWS services or a different compute model entirely.

AWS has good solutions for these problems.

What interests me is how quickly a simple function can turn into a collection of services needed to provide things a traditional application process gives you by default.

In some cases, a FastAPI or Express.js application running as a regular service may already be a better fit, while also letting you take fuller advantage of the ecosystem around those frameworks.

The function stays simple.

The system around it doesn't always do the same.

## What I Wanted Instead

And that is what eventually made me start wondering:

What if I could keep the parts of this model that I like — small functions, events, decoupled services, automatic retries, and a simple developer experience — without tying the application to a specific cloud provider?

For personal projects, I wanted the same kind of speed and simplicity I get from AWS without having to maintain build files, deployment boilerplate, or a collection of infrastructure just to run a few functions and services.

Professionally, the same idea is appealing for a different reason: being able to use an event-driven programming model without making the architecture itself dependent on a specific cloud platform.

And at the same time, I didn't want everything to be a function.

Sometimes a function is the right abstraction.

Sometimes FastAPI or Express.js already gives you everything you need.

What I wanted was a way to use both without giving up the simplicity that made the serverless model attractive in the first place.

## That Became Relay

That idea eventually became Relay.

[Relay](https://github.com/sergiors/relay) is my attempt to keep the developer experience I like from serverless and event-driven platforms, while running on infrastructure I control.

The goal isn't to reproduce AWS service by service. It's to keep the useful abstractions.

I want to be able to write a function, subscribe it to an event, add a schedule, or run a regular service without having to think about build files, containers, workers, retries, or all the infrastructure required to connect those pieces together.

Something closer to:

```yaml
runtime: python3.14

events:
  - handler: events.on_user_created.handler
    pattern:
      recordType: [INSERT]
      tableName: [users]

services:
  - name: api
    entrypoint: app/entrypoint.py
    port: 80
    host: api.example.com
```

At the same time, I still want to be able to run a FastAPI or Express.js application when a regular service is the better fit.

Relay takes care of the infrastructure behind that model, while keeping the application portable and self-hosted.
